# SLO と定常状態

本番の「正常」を数字で決めておく。カオスエンジニアリング（JUK-171）で障害を起こしたときは、この定常状態から外れたか、
外れたことにアラートで気づけたかで結果を見る。アラートの中身は `terraform/grafana/alerting.tf`。

## SLI と SLO

| SLI | 測り方 | SLO |
| -- | -- | -- |
| 可用性 | 死活監視（Synthetic Monitoring `juken-map health`）が `https://juken-map.com/api/health` を叩いて成功した割合。東京とオレゴンから1分ごと。`/api/health` は DB に ping するので、DB が落ちても失敗になる | 30日で 99.5%（品質基準 00 の想定。許される停止は月に約3.6時間） |
| 5xx 率 | `http_requests_total` のうち `status_code` が 5xx の割合 | 5分で 1% 以下 |
| 遅延 | `http_request_duration_seconds` の p95。sign-in・sign-up（ハッシュの計算）と OAuth の callback（外部の待ち）は除く | p95 < 300ms（品質基準 02 の参照 API） |

## 定常状態（2026-10-10 に測った値）

| 指標 | 値 |
| -- | -- |
| 可用性（30日） | 東京 99.995%・オレゴン 100% |
| 5xx（30日） | 0件 |
| リクエスト数（7日） | 約 3.95 万件。うち `/api/health` が1時間に120件 |
| p95・p99（7日） | 17ms・25ms |
| 10分ごとの p95 の最大（7日） | 262ms |
| DB の接続プールの待ち | 0（上限15） |

## 障害とアラートの対応

起こす障害ごとに、鳴るはずのアラートを決めておく。鳴らなかったら、それが見つけた穴になる。

| 障害 | 鳴るはずのアラート |
| -- | -- |
| Go のコンテナが落ちる・EC2 が止まる | 「API（Go）：停止」、死活監視の失敗、「監視の途絶」 |
| nginx・TLS・DNS が壊れる | 死活監視の失敗（`up` は正常のまま） |
| アプリが 5xx を返す | 「5xx率が1%超過」 |
| DB が落ちる・繋がらない | 死活監視の失敗、「5xx率が1%超過」 |
| DB や外部 API が遅い | 「p95 が 600ms を超過」、「DB の接続待ちが続いている」 |
| 接続プールを使い切る | 「DB の接続待ちが続いている」 |
| Alloy が止まる | 「監視の途絶（メトリクス・ログ）」 |

## 分かっている穴

- 遅延のアラートは全ルートをまとめた p95 で見る。リクエストの多くは `/api/health` なので、1つのルートだけが遅くなっても埋もれる
- RDS は `multi_az = false` なので、RDS の再起動中はそのまま止まる
- EC2 は1台なので、EC2 が止まればサービス全体が止まる
