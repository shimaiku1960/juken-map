## 1-1 インデックスと EXPLAIN（2026-10-12）

### 学んだこと

- **`EXPLAIN` は計画、`EXPLAIN ANALYZE` は実際。** `EXPLAIN` は SQL を動かさずに「どの表を、どの索引で、何行くらい読むつもりか」を出す。`EXPLAIN ANALYZE` は実際に動かして、段ごとにかかった時間と読んだ行数を出す。見積もり（`cost=… rows=…`）と実際（`actual … rows=…`）は大きく外れることがある
- **`type` で読み方が分かる。** `ALL` は全件、`ref` は索引で等しい値を探す、`range` は索引で範囲を探す、`eq_ref` は JOIN の相手を一意の索引で1行だけ引く
- **`key_len` で、複合索引の何列目まで使えたかが分かる。** `(userId, date)` の索引で `date` の条件を足すと 766 → 773 に増えた（`date` の7バイト分）
- **`Extra` の `Using filesort` は「索引の順では足りず、読んだあとに並べ替えた」印。** 原因は列が足りないことだけでなく、並べる向きが索引と合わないことでも起きる
- **InnoDB の二次索引には、末尾に主キーが付いている。** `StudyLog_userId_date_idx` は定義上 `(userId, date)` だが、中身は `(userId, date, id)` の並びなので、`ORDER BY date DESC, id DESC` まで索引の順で読める
- **時間は2回目以降で比べる。** 1回目はデータがバッファプール（メモリ）に無く、ディスクから読むので遅い。同じ SQL で 61.3ms → 6.28ms（約10倍）だった
- **索引が効くのは、ごく一部に絞れるとき。** 全体の大半が条件に合うなら、索引で探すより全部読むほうが速く、MySQL は索引を使わない
- **`JOIN` と `LEFT JOIN` の違いは、相手が見つからない行を残すかどうか。** 毎日の通知の SQL は、通知設定が無い人は対象外なので `JOIN`、LINE を連携していない人にもメールは送るので `LineConnection` 側を `LEFT JOIN` にしている

## 1-2 N+1（2026-10-12〜14）

題材は「大学を探す」画面の一覧（`GET /api/universities`）。今の `listForExplore`（`universities.go:57`）は大学 → 学部 → タグを `LEFT JOIN` 1本で取る。これと、わざと N+1 で書いた版（大学の一覧を取ってから、大学ごとに学部、学部ごとにタグを取る）を同じ DB に流して比べた。道具は `apps/api/internal/feature/universities/nplus1_learn_test.go`（`//go:build learn` を付けたときだけ動き、CI では動かない）。

### 学んだこと

- **N+1 は「一覧を1本 ＋ 1件ごとに1本」で SQL が増える書き方。** 手元のデータ（大学 823・学部 66）では、JOIN の 1本に対して N+1 は 1＋823＋66＝**890本**になった。本数は `SHOW SESSION STATUS LIKE 'Questions'` の前後の差で数えた
- **N+1 の時間は「SQL の本数 × 往復1回の時間」でほぼ決まる。** 1本あたり約0.19ms で、DB の中の処理ではなく、アプリと DB の間を行き来する時間が支配する。そのため、キャッシュが冷えていても温まっていても時間はほぼ変わらなかった
- **往復が遠くなるほど差は開く。** 手元は同じマシンの Docker なので往復が近い。SQL 1本ごとに 0.5ms・1ms の遅れを足すと、N+1 は 890回ぶん遅くなるが、JOIN は1回ぶんしか遅くならない。本番は EC2 と RDS が別のマシンなので、手元で測った差より大きくなる
- **JOIN も件数に比例して伸びる。** 予想（JOIN はゆるやかに伸びる）は外れた。全件を返す SQL なので、行が増えればそのぶん遅くなる。違うのは1件あたりの重さで、N+1 は約0.19ms（ほぼ往復1回）、JOIN は約0.003ms。JOIN の伸びを止めるのは LIMIT やページ分け（1-1 の「索引と LIMIT はセット」とつながる）
- **JOIN にも代償がある。** 1対多を JOIN すると親の列が子の数だけ繰り返して並び、1対多が2つ並ぶと行が掛け算で増える。返ってきた平らな行を入れ子に詰め直すコードも要る。間を取る書き方として、大学・学部・タグをそれぞれ `WHERE … IN (…)` で1本ずつ取る（3本）方法がある
- **ベンチマークは1回で判断しない。** 起動直後の1回目は JOIN が 18.7ms だったが、繰り返すと 2.6ms だった（キャッシュが冷えていた分）。`-benchtime=10x` のように回数が少ないとぶれるので、既定の時間で測り直した

| 3 | 繰り返し（`BenchmarkLearnNPlus1`） | 2.6ms | 173.6ms | 約67倍 |

### 面接で話す要点（STAR）

- **S（状況）**：受験生向けアプリの「大学を探す」画面で、大学 → 学部 → タグの入れ子の一覧を返す API がある。大学 823・学部 66 件で、アプリの中で一番重い API だった
- **T（課題）**：「N+1 は遅い」を知識としてではなく、どれだけ・なぜ遅いのかを数字で説明できるようにしたかった
- **A（行動）**：今の JOIN 1本の版と、わざと N+1 で書いた版（890本）を同じ DB に流し、SQL の本数・時間・結果が一致することを Go のベンチマークで比べた。件数を8倍まで増やした比較と、SQL 1本ごとに 0.5ms・1ms の遅れを足して本番の往復を真似た比較もした
- **R（結果）**：手元では約67倍の差（2.6ms 対 174ms）だったが、往復に 1ms 足すと 444倍（3.6ms 対 1,577ms）に開いた。N+1 の時間は「本数 × 往復時間」で決まるので、DB が別のマシンにある本番ほど効くと分かった。一方で JOIN も全件を返す限り件数に比例して伸びるので、件数が増えたら LIMIT やページ分けが要ることも数字で確かめた

## 1-3 トランザクションと分離レベル（2026-10-14〜15）

題材は「スマホと PC の2台から、同時に学習時間を30分足す」場面。アプリの書き換えと同じく「読む → +30 → 書き戻す」形を、2つの `mysql`（A・B）で手で打って再現した。同じ MySQL に別のスキーマ `juken_map_learn` を作り、表 `StudyTotal(userId, minutes)` に `u1 = 60` の1行だけを置いた。実験ごとに 60 へ戻し、終わったら消した。開発用の `juken_map` には触れていない。

### 学んだこと

- **lost update は「読んでから書き戻す」と起きる。** A と B がどちらも 60 を読み、どちらも 90 を書くと、30分が1回ぶん消える（正しくは 120）。`START TRANSACTION` で囲んでも結果は同じで、トランザクションで囲むだけでは防げない
- **`SELECT … FOR UPDATE` は、後から来た方を待たせる。** B は A の COMMIT まで止まり、A が書いた 90 を読んでから 120 を書いた。ロックは文が終わっても外れず、トランザクションが終わる（COMMIT か ROLLBACK）まで続く。そのため autocommit のままの1文では、読んだ直後にロックが外れて意味が無い
- **REPEATABLE READ の普通の SELECT は、始めた時点の写真（スナップショット、MVCC）を読む。** B のトランザクション中に A が 90 を確定しても、B の普通の SELECT は 60 のままだった。実験1で両方が 60 を読んだのはこのため
- **`FOR UPDATE` は写真を見ずに、確定済みの最新の行を読んでロックする。** 同じ B のトランザクションの中でも、普通の SELECT は 60、`FOR UPDATE` は 90 を返した
- **READ COMMITTED は、普通の SELECT のたびに写真を撮り直す。** B が同じ SELECT を2回打つと 60 → 90 と変わった。同じ行を読み直すと値が変わることを non-repeatable read と言い、REPEATABLE READ はこれが起きないことから名前が付いている
- **分離レベルが変えるのは「普通の SELECT に何が見えるか」だけ。** READ COMMITTED にしても、A と B がほぼ同時に 60 を読めば lost update は起きる（実験はしていない）。防ぐのは行のロック（`FOR UPDATE`）か、読まずに DB の中で足す `SET minutes = minutes + 30`（実験はしていない）
- **このリポジトリが既定の REPEATABLE READ のままで足りている理由。** 読んでから書き戻す更新は `FOR UPDATE` で読んでいる。学習記録の書き換え `UpdateLog`（`write/studyrecord/log.go:108`）と、LINE 連携の nonce を使い切る `CompleteAccountLink`（`write/notification/line.go:60`）がそう。`FOR UPDATE` の読み取りは分離レベルによらず最新を読むので、分離レベルを変えても得るものが無い。違いが出る普通の SELECT は画面に出すための読み取りで、ほかの人の更新が一瞬遅れて見えても困らない

### 数字で見た結果

A は既定の REPEATABLE READ・autocommit のまま、B のトランザクションの途中で 90 を確定させた。

| 実験 | B の分離レベル | B の読み方 | B が読んだ値 | 最終の値 |
| -- | -- | -- | -- | -- |
| 1 | REPEATABLE READ | 普通の SELECT | 60 | **90**（lost update） |
| 2 | REPEATABLE READ | `FOR UPDATE` | 90（A の COMMIT まで待った） | **120** |
| 3 | REPEATABLE READ | A の確定のあとに、普通の SELECT と `FOR UPDATE` | 60 と 90 | — |
| 4 | READ COMMITTED | A の確定の前後に、普通の SELECT を2回 | 60 → 90 | — |

### 変えたこと

本番のコードは変えていない。読んでから書き戻す更新は、すでに `FOR UPDATE` で守られている。

### 面接で話す要点（STAR）

- **S（状況）**：受験生向けアプリで、学習記録を書き換える API は「今の行を読む → 値を変える → 書き戻す」形をしている。同じ人がスマホと PC から同時に書き換えることがありうる
- **T（課題）**：アプリが `SELECT … FOR UPDATE` を使っている理由と、分離レベルを既定の REPEATABLE READ のままにしてよい理由を、実際に起きることで説明できるようにしたかった
- **A（行動）**：MySQL のセッションを2つ開き、「2台から同時に30分足す」を手で再現した。読み方（普通の SELECT と `FOR UPDATE`）と、分離レベル（REPEATABLE READ と READ COMMITTED）を変えて、それぞれが読む値と最終の値を比べた
- **R（結果）**：普通の SELECT では、60 に30分を2回足して 90 になる lost update を再現した。`FOR UPDATE` では後の方が先の COMMIT を待ち、正しく 120 になった。分離レベルの違いは普通の SELECT の写真の撮り方だけで、`FOR UPDATE` はどちらでも最新を読む。なので、書き換えを `FOR UPDATE` で守っているこのアプリでは、分離レベルを変える必要が無いと説明できるようになった

## 1-4 コネクションプール（2026-10-15）

Go の `database/sql` のプールを、`-tags learn` のときだけ動くテスト（`apps/api/internal/database/pool_learn_test.go`）で試した。手元の DB に繋ぎ、表には触れず `SELECT 1`・`SELECT SLEEP(0.02)`・`SELECT BENCHMARK(50000, SHA2(...))` だけを流した。プールの上限は本番と同じ15本（`database.go` の `SetMaxOpenConns(15)`）を基準に変えた。計画では k6 でアプリ全体に負荷をかける予定だったが、本数がコードに固定されていて外から変えられず、データの用意も大きいので、テストの中で50人ぶんの負荷をかける形に変えた。

### 学んだこと

- **プールは接続を使い回す置き場で、上限まで貸したら次の人は空くまで待つ。** SQL を1本流すときは、流している間だけ借りて、結果を読み終えたら返す。トランザクションは `BeginTx` から `Commit` / `Rollback` まで1本を借りっぱなしにする
- **トランザクションの中で `tx` ではなく `db` を使うと、自分が持っている接続を自分で待つ。** 上限1本では、1人だけで止まった（実験1）。MySQL の中のデッドロックではなく、アプリのプールの中の行き詰まりなので、MySQL は気づけない。タイムアウトが無ければ永遠に止まる
- **その間違いは、人数が少ないと表に出ず、ある人数で全員が止まる。** 上限15本で、14人までは全員が0.2秒で成功し、15人で全員が失敗した（実験2）。トランザクションを持つ人数が14以下なら、残りの1本を順番に使い回せる。15になると空きが0で、全員がほかの誰かが返すのを待ち、誰も返さない。本番では `withDeadline`（`server.go` の `requestTimeout`、10秒）まで止まって失敗し、その間はプールが空かないので関係のない API も待たされる。`InTx` は `fn` に `tx` を渡す作りだが、クロージャの中から外の `db` を使うことはできてしまうので、トランザクションの中では `tx` だけを使うと決めて読むこと
- **DB に余裕があるときは、プールの本数がそのまま同時に流せる SQL の数になる。** 50人が20ms の SQL を流し続けると、終わった本数は上限に比例した（実験3）。1本の時間の大半は接続待ちで、上限が足りないと平均より p95 が大きく悪くなる（空いた接続は順番どおりに回ってこない）
- **必要な本数は「1秒あたりの本数 × 1本の時間」で見積もれる。** 実験3の上限15本は 630本/秒 × 0.024秒 ≒ 15本で、ちょうど使い切っていた。本番のピーク100RPS で SQL が1本5ms なら 0.5本で、15本は十分に余る
- **DB の CPU が足りないときは、プールを増やしても速くならず、増やしすぎると遅くなる。** CPU を使う SQL では、上限2でも5でも1秒あたり約73本で頭打ちになり、上限10以降は本数が減った（実験4）。上限50ではプールの待ちが0になったが、中央値は最も遅い805ms で、待ち行列がアプリから MySQL の中へ移っただけだった
- **プールの本数は、アプリに来る人数ではなく、DB が同時にさばける量で決める。** 少なすぎるとアプリで順番待ちが起き、多すぎると DB の CPU を取り合う。プールは DB に押し寄せる量を抑える蛇口でもある。CPU のほか、ディスクの読み書きや MySQL の `max_connections`（手元は既定の151）もさばける量に入る

### 変えたこと

本番のコードは変えていない。上限15本は、本番の負荷（ピーク100RPS）に対して十分に余っている。変えるときは `load-tests/` で測る。

### 面接で話す要点（STAR）

- **S（状況）**：Go の API は `database/sql` のプールを上限15本で使い、書き込みは `InTx` でトランザクションにまとめている
- **T（課題）**：プールの上限をどう決めるのか、トランザクションとプールの組み合わせでどんな事故が起きるのかを、数字で説明できるようにしたかった
- **A（行動）**：学習用のテストで、トランザクションの中から `db` で SQL を流す間違いを、人数を変えて再現した。さらに50人の負荷をかけ、待つだけの SQL と CPU を使う SQL のそれぞれで、プールの上限を変えて本数と p95 を比べた
- **R（結果）**：間違ったコードは14人までは正常に動き、15人で全員が止まることを示した。少人数のテストでは見つからず、本番でサービス全体を止める種類の不具合だと説明できる。上限は、DB に余裕があるときは増やすほど速くなるが、DB の CPU が足りないときは増やしても速くならず、50本では待ち行列が MySQL の中へ移るだけだった。本数は DB が同時にさばける量で決め、見積もりは「1秒あたりの本数 × 1本の時間」で出せる
