## S1. 全体像と入り方（SSH と SSM）（2026-10-14〜15）

- **やったこと**：
  - `aws sts get-caller-identity` で、CLI がどの IAM の主体として AWS を触っているかを確かめた
  - `describe-instances` で EC2 に付いているセキュリティグループを見た。22番を開けている `launch-wizard-1` は付いておらず、22番は閉じている
  - SSM で本番に入り、`whoami`・`id`・`hostname`・`uptime`、OS・CPU・メモリ・ディスクを見た
  - 使い捨てのコンテナ（`ubuntu:24.04`）で `ssh-keygen` を実行し、`~/.ssh` と鍵のパーミッションを見た。秘密鍵を `chmod 644` にすると、root で実行しても `UNPROTECTED PRIVATE KEY FILE` で読み込みを拒まれた。600 に戻すと読み込めた
  - 本番の構成図を描いた（利用者の経路と運営者の経路）
- **理解したこと**：
  - 利用者の経路は「ブラウザ → CloudFront（443）→ EC2 の nginx（443、SG で CloudFront の IP だけ許可）→ Go のコンテナ（127.0.0.1:8080/8081）→ RDS（3306、SG で EC2 からだけ許可）」
  - SSM は Mac も EC2 も自分から外の SSM へ 443 でつなぎに行くだけなので、外から入る 22番を開けなくてよい。認証は IAM でまとめて管理でき、操作は CloudTrail に記録される
  - パーミッションは r=4・w=2・x=1 の合計を、持ち主・グループ・その他の順に並べたもの。ディレクトリの `x` は「中に入れる」
  - 秘密鍵（600）は読めた人が本人としてログインできるので、自分以外に読ませない。公開鍵（644）は照合に使うだけで、秘密鍵を計算できないので見られてよい
  - `~/.ssh`（700）を閉じるのは、ファイルの削除・すり替えはディレクトリの `w` で決まるため。他人が `authorized_keys` に鍵を書き足せると、その人が本人として入れてしまう
  - ssh は「誰が実行したか」ではなく「鍵が漏れうる状態か」を見て拒む。sshd 側も `StrictModes` で同じ確認をする
  - コンテナはイメージ（読み取り専用のひな形）から作る実体。Mac では Docker Desktop の Linux VM の中で動く。`--rm` なら抜けると変更ごと消える
- **つまずいた点**：
  - 構成図を「画面 → API → DB」というアプリの流れで描いてしまい、通る箱（CloudFront・nginx・コンテナ）とポートの層が描けなかった
  - SSM の経路は「ID と認証を確かめる」までしか分からず、矢印の向き（EC2 から外へつなぐ）が出てこなかった
  - 複数行をまとめて貼ると、`apt-get install` の実行中に後ろの行が読み捨てられた
- **次回やること**：S2（ユーザー・グループ・パーミッション）。今回の `rwx` の読み方を、本番のユーザーとグループで確かめる
