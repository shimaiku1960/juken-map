# 信頼性

バックエンドの学習計画（`docs/learning/README.md`）の「3. 信頼性」で学んだことのまとめ。回ごとに節を足していく。

## 3-1 タイムアウトの値の関係（2026-10-25）

題材は API の入口から外部 API までの各層のタイムアウトと、止めるときの待ち時間。実験は `apps/api/internal/app/timeout_learn_test.go`（`-tags learn` のときだけ動く）で、本物の `withDeadline` と `requestTimeout` を使い、`httptest` のサーバーに対して流した。DB と本番には触れていない。

### 学んだこと

- **内側ほど短くする。** 内側（ハンドラの ctx の上限）が先に来れば、ハンドラが自分で 500 と理由を書いて返せる。外側（`WriteTimeout`・nginx）が先に来ると、呼び出し側には何も届かず、サーバーのログにも理由が残らない（実験1・2）
- **Go の `WriteTimeout` は「その時刻を過ぎたら書き込みを失敗させる」期限で、その時刻に接続を切るものではない。** ハンドラは期限に気づかずに最後まで仕事をし、書こうとした時点で失敗して接続が閉じる。仕事は成功しているのに、呼び出し側には失敗に見える（実験2）。学習記録の作成なら、保存されたのにエラーが出て、押し直すと2件になる（2-2 の冪等性）
- **`context.WithTimeout(親, d)` の締め切りは、親の締め切りと d 後の早いほう。** 内側に外側より長い値を書いても、黙って外側の値に切り詰められる。エラーも警告も出ない（実験3）
- **`http.Server.Shutdown` が待つのは処理中のリクエスト（接続）だけで、`go f()` で始めた goroutine は待たない。** 応答を返したあとの仕事は、`Shutdown` が戻って `main` が終わった時点で、途中でも消える（実験4）
- **止めるときにも大小関係がある。** `docker stop` の猶予 > `Shutdown` で待つ時間 > 止めるときに残っている仕事にかかる時間、の順でないと、猶予を過ぎたところで SIGKILL が来るか、仕事が途中で消える

| 層 | 値 | 場所 |

理由のある大小（守られているもの）。

- `requestTimeout` 10秒 < `WriteTimeout` 15秒：打ち切る前に 500 を返すため（`server.go:16-17` のコメント、実験1・2）
- 外部 API 5秒 < `requestTimeout` 10秒：外部 API が止まっても、ハンドラが自分でエラーを返せる
- `WriteTimeout` 15秒 < CloudFront 30秒 < nginx 60秒：Go が先に諦める
- 毎日の通知は、`SetWriteDeadline` で書き込み期限を 50 + 10 秒に延ばし、ctx をリクエストの上限から切り離している。nginx の60秒とちょうど同じなので、通知が上限いっぱいかかると nginx 側と同時になる

矛盾している組み合わせ（3-2・4 で扱う）。

| 組み合わせ | 起きること | 扱う回 |
| -- | -- | -- |
| `parseTimeout` 20秒 > 外側の `requestTimeout` 10秒 | 20秒待つつもりが10秒で 500。スキーマを変えた直後の初回（約10秒）が落ちうる | 3-2 か別の Issue（ルートごとの上限か、20秒をやめるか） |
| 応答のあとのメール 30秒、`Shutdown` は goroutine を待たない | デプロイの直前に送り始めたメールが、ログも残さず消える | 3-2（止めるときに待つ）、4（outbox） |
| `docker stop` の猶予 10秒 = `Shutdown` 10秒 | `Shutdown` が終わる前に SIGKILL が来うる。猶予を少し長くする | 3-2 |

### 面接で話す要点（STAR）

- **S（状況）**：API は CloudFront → nginx → Go の順に通り、Go の中にも1リクエストの上限・`WriteTimeout`・外部 API の上限がある。止めるときは `docker stop` → `Shutdown` の順で、応答のあとにメールを goroutine で送っている
- **T（課題）**：値がばらばらに決まっていて、大小に理由があるか、逆だと何が起きるかを説明できなかった
- **A（行動）**：全部の値を1枚の表にし、外側から内側へ並べた。本物の `withDeadline` を使って、上限と `WriteTimeout` の大小を入れ替えたときに呼び出し側へ何が届くか、長い上限を内側に書いたらどうなるか、`Shutdown` が応答のあとの仕事を待つかを、ローカルで試した
- **R（結果）**：今の順番では10秒で 500 と理由が返り、逆にすると仕事は成功したのに18秒後に無言で切断された。内側に書いた20秒は黙って10秒に切り詰められ、`Shutdown` は応答のあとのメールを0秒しか待たなかった。「内側ほど短く」「止めるときは猶予 > Shutdown > 残りの仕事」という原則と、その原則に反している3か所を、数字つきで説明できるようになった

## 3-2 止めるときに「応答のあとの仕事」を待つ（2026-10-25）

3-1 の実験4で見つけた「`Shutdown` は `go f()` で始めた仕事を待たない」を、本物の API で確かめて直した。実験は `apps/api/internal/app/shutdown_learn_test.go`（`-tags learn` のときだけ動く）で、`go build` した本物のサーバーを別のプロセスとして起動する。サインアップを5件送り、5件とも 200 が返った直後に SIGTERM（デプロイの `docker stop` と同じ）を送って、確認メールが何通届くかを数えた。Resend は偽物（1通に3秒、`LEARN_MAIL_DELAY` で変えられる）、DB はテスト用の `juken_map_test` を使い、本番には触れていない。

### 学んだこと

- **Go のプロセスは、`main`（このリポジトリでは `os.Exit`）に着いた時点で、ほかの goroutine を待たずに終わる。** `run` が戻る → `Main` が戻る → `os.Exit`、と一直線に進むので、応答のあとに `go f()` で始めたメールは途中で消える
- **黙って消えるのは、「失敗した」と書く処理も同じ goroutine の中にあるから。** 成功（`sent`）も失敗（`Failed to send.`）も、Resend の答えが返ってきたあとに書く。答えを待っている最中にプロセスが消えると、どちらの行にも着かない。記録は消える側ではなく、生き残る側（止める処理）に書かせる
- **待つ仕組みは「数える」と「0 になるまで止まる」。** 仕事を始めるときに +1、終わったら -1 し、止めるときは `sync.WaitGroup.Wait` で 0 になるまで `run` から戻らない。`Wait` はループで数を見に行くのではなく、眠って、最後の `Done` に起こしてもらう
- **待つ時間には上限を付け、超えたら残した数を書く。** 上限なしだと、終わらない仕事が1つあるだけで止まれない
- **止めるときの値も「内側ほど短く」。** 外部 API 5秒 < 止めるときに待つ時間 20秒 < `docker stop` の猶予 30秒。Resend が遅くても、内側の5秒で諦めて失敗と書くので、20秒の上限まで届かない（実験3）
- **止め始めたあとに来る仕事を全部断ると、2段の仕事が落ちる。** パスワード再設定は「準備の仕事」の中で「メールの仕事」を始める（`recovery.go:85`）。動いている仕事が始めた続きは受け、全部終わってから来たものだけ断る

### 数字で見た結果

| 実験 | 偽の Resend | SIGTERM から終了まで | 受け取った | 送り終えた | ログ |
| -- | -- | -- | -- | -- | -- |
| 1 変える前 | 1通3秒 | 0秒 | 4通 | **0通** / 5通 | 何も残らない |
| 2 変えたあと | 1通3秒 | 3秒 | 5通 | **5通** / 5通 | （全部届いた） |
| 3 変えたあと | 1通10秒 | 5秒 | 5通 | 0通 / 5通 | 失敗 5件（外部 API の上限5秒で諦めた）、残した仕事 0回 |

実験1で「受け取った」が4通なのは、残りの1通が送信回数の上限の確認（DB）の途中で消え、Resend まで届かなかったから。

| ファイル | 変更 |

- 失敗したメール（実験3）と、20秒で残したメールは送り直されない。誰宛てだったかも分からない → テーマ4（outbox）
- 3-1 の表の `parseTimeout` 20秒が外側の10秒に切り詰められる件は、まだ扱っていない

### 面接で話す要点（STAR）

- **S（状況）**：サインアップやパスワード再設定のメールは、応答を返したあとに goroutine で送っている。デプロイでは `docker stop` が古い API に SIGTERM を送り、API は `http.Server.Shutdown` で処理中のリクエストを返し終えてから終わる
- **T（課題）**：`Shutdown` は goroutine を待たないので、デプロイの直前に始めたメールが途中で消える。失敗のログも同じ goroutine の中で書くので、消えたことが記録に残らない
- **A（行動）**：本物のサーバーを別のプロセスで起動し、サインアップ5件の直後に SIGTERM を送って、偽の Resend で届いた数を数えた。応答のあとの仕事を数える小さな部品を作り、止めるときは `Shutdown` のあとに数が 0 になるまで（上限20秒）待ち、超えたら残した数をログに出すようにした。外部 API 5秒 < 待つ時間 20秒 < `docker stop` の猶予 30秒の順に値を揃えた
- **R（結果）**：届いたメールは5通中0通から5通になり、止まるまでの時間は0秒から3秒（1通にかかる時間）になった。Resend が遅いときも、5秒で失敗とログに残り、黙って消える経路がなくなった。送り直しは outbox（テーマ4）の課題として切り出した
