# バックエンドの学習計画（受験マップを教材にする）

受験マップのコードを教材にして、実務で通用するバックエンドの知識を「自分のプロダクトの中で」学ぶための計画。
2026-10-12 時点のコードを読んで、テーマごとに「今どうなっているか」「足りない点・伸ばせる点」を診断し、学ぶ順番を決めた。

テーマを1つ終えるごとに `docs/learning/<テーマ名>.md` に、学んだこと・変えたこと・数字で見た結果・面接で話す要点
（STAR、日本語と英語）をまとめる。

## 進め方の決まり

- 1回に1テーマ。ブランチは `learn/<テーマ名>`（作業は `pnpm wt:new learn/<テーマ名>` で作る worktree の中で行う）
- ①概念（なぜ必要か・無いと何が困るか）→ ②このリポジトリのどこに関係するか → ③自分で考える問い → ④試したあとで段階的に実装
- コードは短さより、1ステップずつ追える書き方を優先する
- 実装の前に、変えるファイルと中身を説明して確認を取る
- 改善したらテストを書き、変更前と変更後を数字で比べる（クエリ時間・レイテンシ・件数）
- **ローカルだけで作業する。** 本番（AWS・RDS・`terraform apply`）には触れない。負荷試験もローカルの DB とアプリに向ける
- このリポジトリは public なので、**直していないセキュリティの穴はここに書かない**（GitHub Security Advisory で扱う）

## 構成（認識との違い）

| 最初の認識 | 実際のコード |
| -- | -- |
| Vite + Fastify の分離構成 | **Vite（React 19）の SPA + Go の API**。Fastify（Node）は 2026-09 に Go へ移し終えて削除済み（JUK-70）。本番は Go が API・ログイン・ビルド済みの画面をすべて配る（JUK-111・JUK-115） |
| MySQL 8.4（本番は RDS） | そのとおり。ORM は使わず `database/sql` で SQL を直接書く。本番は `db.t4g.micro`・`multi_az = false` |
| Terraform | そのとおり（`terraform/`）。Grafana のアラートも Terraform（`terraform/grafana/alerting.tf`） |
| GitHub Actions | そのとおり。CI（lockfile・check・go・e2e）、main へのマージで EC2 へ自動デプロイ（スモークテストと自動ロールバックつき） |
| OpenTelemetry + Prometheus/Loki/Tempo/Grafana | ローカルは docker-compose でそのとおり。**本番は Alloy が集めて Grafana Cloud へ送る** |
| Vitest / Playwright | そのとおり。加えて **Go の `go test`**（`dbtest` タグを付けると本物の MySQL に流す） |
| （無し） | **k6 の負荷試験がすでにある**（`load-tests/`）。Redis は使っていない（キャッシュはプロセスのメモリ） |

API の中は「入口（`internal/httpx/router.go`）→ ハンドラ（`internal/feature/*`）→ ストア（SQL）」の順に呼び、
書き込みは表の持ち主（`internal/write/*`）に集めてある。詳しくは `docs/architecture.md` と `apps/api/README.md`。

## 診断

全体として、ポートフォリオとしてはかなり作り込まれている。「何も無いところに足す」より、
**すでにある仕組みを自分の言葉で説明できるようにし、残っている穴を数字つきで埋める**ほうが学びになる。

凡例：◎ 実務水準でできている ／ ○ できているが伸ばせる ／ △ 足りない

### 1. DB

| 項目 | 現状 | 判定 |
| -- | -- | -- |
| インデックス設計 | `(userId, date)` の複合索引を足し、毎日の通知の SQL が 268ms → 1.75ms（36.9万行で計測、`db/migrations/20260915090000_add_user_date_indexes`）。左端が同じで要らない索引を同じ ALTER で消している | ◎ |
| EXPLAIN | 計測はしているが、`EXPLAIN` / `EXPLAIN ANALYZE` の出力（type・key・rows・Extra）を読んで説明した記録がリポジトリに無い | △ |
| N+1 | 「1対多は JOIN 1本、1対多が並ぶときは SQL を分ける」と方針がある（`docs/architecture.md`）。目立つ N+1 は見当たらない | ○ |
| トランザクション・分離レベル | 更新の前に `SELECT ... FOR UPDATE` で行を押さえ、lost update を防いでいる（`internal/write/*`）。分離レベルは既定の REPEATABLE READ のまま。なぜそれで足りるかを説明できるか、が学びどころ | ○ |
| コネクションプール | 最大15本・接続は3分で張り直す（`internal/database/database.go`）。待ちはメトリクス（`go_sql_wait_duration_seconds_total`）とアラートがある | ◎ |
| マイグレーション | `GET_LOCK` で二重適用を防ぎ、失敗したら記録を残して止まる（`internal/migrate/migrate.go`）。DB ユーザーも DML 用・DDL 用で分けてある。**足りないのは「古いアプリと新しい表が同時に動く時間」への備え**：デプロイは新旧のコンテナが並んでから切り替えるので、列の削除・名前変更をそのまま書くと古いコンテナが壊れる。expand → migrate → contract の手順と、`ALGORITHM=INSTANT/INPLACE` の確かめ方が文書に無い | △ |
| スロークエリの観測 | 本番の RDS はパラメータグループが既定で、スロークエリログが無い（トレースで SQL 1本ずつの時間は見える） | △ |

### 2. API 設計

| 項目 | 現状 | 判定 |
| -- | -- | -- |
| エラー設計 | 形は `{"error", "code", "reqId"}` に統一し、OpenAPI に code の一覧がある（`internal/httpx/errors.go`、`openapi/openapi.yaml`）。`reqId` でログと突き合わせられる | ◎ |
| バリデーション | Zod（画面）と Go の手書き（`internal/httpx/validate.go`）の二重。禁止項目を混ぜても書き換わらないことを DB に流すテストで確かめている | ◎ |
| ページネーション | 学習記録・予定の一覧は期間で絞ったうえで **最大1000件で打ち切る**だけ（`internal/feature/study/study.go` の `MaxLogs`）。管理画面の大学一覧は `LIMIT ? OFFSET ?` | △ |
| 冪等性 | 学習記録の作成に冪等キーが無い（保存は成功したが応答だけ失われ、押し直すと2件になる）。※本番に入れるかは以前「今は入れない」と判断済み。学習としては扱い、入れるかは改めて決める | △ |
| バージョニング | `/api/v1` のような版は無い。画面と API が同じイメージで同時に入れ替わるため、今は要らない。**要らない理由と、要るようになる条件**を説明できることが学び | ○ |

### 3. パフォーマンス

| 項目 | 現状 | 判定 |
| -- | -- | -- |
| 負荷試験 | k6 で限界点を段階的に測る（`load-tests/limit.js`、結果は `load-tests/results/`）。本番相当の AWS 環境用の Terraform もある | ◎ |
| キャッシュ | 大学一覧・参考書マスターを「JSON + gzip + ETag」でメモリに10分持つ（`internal/httpx/json_snapshot.go`） | ○ |
| Redis | 使っていない。EC2 1台なので今は不要。**台数を増やしたときに何が壊れるか**（メモリのキャッシュ・回数制限の数がサーバーごとにばらける）を説明できるのが学び | ○ |
| ボトルネックの計測 | 「本番の1リクエストのうち DB は1ms未満で、主因は通信」と分かっている。ルートごとに p95 を見る道具（トレース・ダッシュボード）はある | ○ |

### 4. 非同期処理

| 項目 | 現状 | 判定 |
| -- | -- | -- |
| 毎日の通知 | GitHub Actions の cron が API を叩き、goroutine 5本で送る。メールは毎秒5通に間隔を空ける。**送る前に「送った印」を入れ、失敗したら印を消す**ので、二重送信を防ぎつつ次の実行で送り直せる（`internal/feature/notifications/notifications.go`） | ○ |
| 確認メール・パスワード再設定のメール | 応答を返したあと **素の `go f()` で送る**（`internal/feature/auth/handlers.go` の `cfg.Async`）。失敗はログに残すだけでリトライが無く、送信中にデプロイでプロセスが止まると消える | △ |
| ジョブキュー | 無い。キューを入れるなら Redis を足すより、まず **MySQL の表をキューにする（outbox）** のが今の規模に合う | △ |

### 5. 信頼性

| 項目 | 現状 | 判定 |
| -- | -- | -- |
| レート制限 | 2種類を目的で使い分けている。認証は総当たりを止めるので DB で数える（数え漏れを許さない）、利用者単位はメモリのトークンバケット（読み 120/秒2、書き 30/秒0.5）。同時処理数の上限（160）を超えたら待たせず 503 | ◎ |
| タイムアウト | 1リクエスト10秒（`withDeadline`）、`WriteTimeout` 15秒、ヘルスチェックの DB ping 2秒、外部 API にも上限。**それぞれの値の関係**（なぜ 10 < 15 なのか）を説明できるのが学び | ○ |
| グレースフルシャットダウン | SIGTERM で `Server.Shutdown`（最大10秒）。デプロイは nginx を新しいコンテナへ向け替え、5秒待ってから古い方を止める。**ただし上の「応答のあとで送るメール」は待たずに切られる。** また `docker stop` の猶予（既定10秒）と `Shutdown` の上限（10秒）が同じで、余裕が無い | △ |
| ヘルスチェック | `/api/health` が DB に ping する（`internal/app/http.go`）。デプロイのスモークテストと死活監視が同じものを使う。**liveness（プロセスが生きているか）と readiness（受けられるか）を分けていない**ので、DB が落ちると「アプリも落ちている」扱いになる。1台構成ではそれで困らない理由と、困る条件を説明できるのが学び | ○ |

### 6. セキュリティ

| 項目 | 現状 | 判定 |
| -- | -- | -- |
| 認証・セッション | Go で自作（JUK-115）。セッションは DB、Cookie は HttpOnly・Secure・SameSite=Strict（`internal/feature/auth/session.go`）。管理者は TOTP の2段階認証 | ◎ |
| 認可 | ルートを「入口の種類」ごとに別の関数で登録し、ログイン必須のハンドラはセッションを引数で受け取る＝**取り違えがコンパイルで分かる**（`internal/httpx/router.go`）。他人の ID を断ることを DB に流すテストで全ルート確かめる | ◎ |
| SQL インジェクション | プレースホルダ `?` で渡す。列名など値でないものを組み立てる箇所の見分け方が学び | ◎ |
| CSRF | セッションの Cookie の SameSite=Strict に加え、Go 標準の `http.CrossOriginProtection`（`Sec-Fetch-Site` / `Origin`）で別サイトからの書き込みを断る | ◎ |
| 秘密情報 | AWS Secrets Manager（`terraform/secrets.tf`）。DB ユーザーを役割で分けている | ◎ |

ここは「足す」より **なぜこの形にしたかを面接で説明できるようにする**テーマ。穴を見つけても public な場所には書かない。

### 7. 可観測性

| 項目 | 現状 | 判定 |
| -- | -- | -- |
| 計装 | OpenTelemetry のトレース（リクエスト・SQL 1本ずつ・外部 API）、Prometheus のメトリクス、構造化ログ（Loki）。トークンをスパンに残さない | ◎ |
| SLI / SLO | 可用性 99.5%・5xx 1%以下・p95 < 300ms を決め、定常状態を測ってある（`docs/slo.md`） | ○ |
| アラート設計 | しきい値型（「5xx率が1%超を1分」「p95 が600ms超」）。**エラーバジェットとバーンレート（どれだけの速さで予算を使っているか）で鳴らす形になっていない**。p95 は全ルートまとめてなので、`/api/health` に埋もれて1本のルートの遅れに気づけない（`docs/slo.md` の「分かっている穴」） | △ |

### 8. テスト

| 項目 | 現状 | 判定 |
| -- | -- | -- |
| DB を使う統合テスト | `dbtest` タグのテストが本物の MySQL（`juken_map_test`、本番と同じマイグレーション・同じ DML だけの権限）に流れる | ◎ |
| テストしやすい設計 | 通知は DB と送信先をインターフェースで差し替えられる。セッションの読み方も関数で受け取る | ◎ |
| テストどうしの独立 | テスト用 DB を全テストで共有している。**並列に流したとき・データが残ったときにどう干渉するか**、トランザクションで巻き戻す方式・使い捨てコンテナ（Testcontainers）との比較が学び | ○ |
| 計測のテスト | 速さを守るテスト（「この一覧は SQL 1本で取る」「この SQL は索引を使う」）は無い | △ |

## 学ぶ順番

**面接で聞かれやすい順** と **今のコードですぐ試して数字を出せる順** の両方で並べた。
前のテーマで作ったもの（計測の道具・テストの書き方）を、後のテーマで使い回せるようにしてある。

| 順 | テーマ（ブランチ） | 主にやること | 数字で比べるもの | 面接で効く場面 |
| -- | -- | -- | -- | -- |
| 1 | DB（`learn/db`） | 下の5回に分ける | クエリ時間・読んだ行数 | 日本の新卒面接で最も聞かれる。北米のシステム設計でも土台 |
| 2 | API 設計（`learn/api-design`） | 一覧をカーソル式のページネーションにする（OFFSET との差を EXPLAIN で見る）、学習記録の作成に冪等キー | 深いページの応答時間、二重送信で増える件数 | 北米の API 設計の定番。1 の EXPLAIN をそのまま使う |
| 3 | 信頼性（`learn/reliability`） | タイムアウトの値の関係を図にする、シャットダウンで「応答のあとの仕事」を待つ、liveness と readiness | 停止中に失われるリクエスト・メールの数 | SRE の面接で必ず聞かれる |
| 4 | 非同期処理（`learn/async-jobs`） | メールを MySQL の表をキューにした方式（outbox）へ。リトライ・指数バックオフ・諦めた仕事の置き場 | 送信失敗を起こしたときに最終的に届いた割合 | システム設計の定番。3 で見つけた穴をそのまま直す |
| 5 | テスト（`learn/testing`） | テスト DB の独立のさせ方、「SQL の本数」「索引を使うこと」を守るテスト | テストの実行時間、並列で流したときの失敗数 | 「どうやって壊れていないと分かるのか」に答えられる |
| 6 | パフォーマンス（`learn/performance`） | k6 でローカルの限界点を測る、プロファイル（pprof）でボトルネックを見る、Redis を足したら何が変わるかを試す | RPS・p95・CPU | 北米のシステム設計（キャッシュ・スケール） |
| 7 | 可観測性（`learn/observability`） | ルートごとの SLI、エラーバジェットとバーンレートのアラートをローカルの Grafana で組む | 障害を起こしてから気づくまでの時間 | SRE 志望なら強い武器 |
| 8 | セキュリティ（`learn/security`） | 既存の守り（CSRF・認可・回数制限）を、外したら何が通るかで確かめて説明できるようにする | 外したときに通ってしまう攻撃の数 | すでに作り込まれているので、説明の練習が中心 |

### 1. DB の中身（5回に分ける）

| 回 | 内容 | このリポジトリの題材 |
| -- | -- | -- |
| 1-1 | インデックスと EXPLAIN の読み方 | 学習記録の一覧・毎日の通知の SQL。`(userId, date)` を一度外して、EXPLAIN の `type`・`key`・`rows`・`Extra` がどう変わるかを見る |
| 1-2 | N+1 | わざと N+1 で書いた版と今の JOIN の版を、件数を増やしながら時間と SQL の本数で比べる |
| 1-3 | トランザクションと分離レベル | 2つの `mysql` を開いて、`FOR UPDATE` の有無で lost update が起きるのを再現する。REPEATABLE READ と READ COMMITTED の違い |
| 1-4 | コネクションプール | トランザクションの中で別の接続を借りるとどうなるか（プールを使い切って止まる）。プールの本数を変えて k6 で比べる |
| 1-5 | マイグレーションの安全な運用 | 列の名前変更を「expand → 移行 → contract」の3つに分けて書く。新旧のコンテナが並ぶ間に壊れないことを確かめる |

## 注意

- 新しいマイグレーションを足すブランチは、ローカルの全 worktree の DB も変わる（DB のコンテナを共有している）。また main へ入れる PR は、CI が通ってもマージ前にユーザーが確認する
- 学習用に作った大きなデータは、本番と同じ `juken_map` ではなく別のスキーマ（例: `juken_perf`）に置く
- 学習で作った変更を本番に入れるかは、テーマごとに改めて決める（学びのために作ったものが、本番にとって良いとは限らない）
