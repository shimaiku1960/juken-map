## 2-1 ページネーション（OFFSET とカーソル）（2026-10-21）

題材は管理画面の利用者一覧（`feature/admin/users.go` の `listUsers`）。同じ MySQL の別スキーマ `juken_perf` に、本番の `user` と同じ形の表 `user_page` を `CREATE TABLE ... LIKE` で作り、50万人を入れた。`id` は MD5 の32文字で、`createdAt` は1分ずつずらし、3人ずつ同じ時刻にした（同じ時刻の人が並ぶときの扱いを見るため）。開発用の `juken_map` には触れていない。

### 学んだこと

- **OFFSET は「先頭から何行捨てるか」で、捨てる行も一度は読む。** `LIMIT 50 OFFSET 499950` は、49万9950行を読んで捨ててから50行を返す。そのため、深いページほど遅くなる。索引が無いと、並べ替えに入れる行も 50 → 5万 → 50万と、ページに比例して増えた（実験1）
- **索引を足しても、速くなるのは浅いページだけ。** `(createdAt DESC, id)` の索引で、1ページ目は50行だけ読んで終わるようになった。一方、最後のページでは MySQL が索引を使わなかった。索引には `email` が無いので、索引をたどると1行ごとに表の本体へ取りに戻る。50万回戻るより全部読んで並べ替えるほうが速いと、MySQL が判断した（実験2）
- **カーソル式は、前のページの最後の行を「しおり」にして、索引でその位置へ直接飛ぶ。** しおりは並び順の列（`createdAt` と `id`）の値。捨てる行が無いので、どのページでも読むのは50行で、時間はページの深さによらない（実験3）
- **並び順の列だけでは1行に決まらないときは、最後に一意の列を足す。** 3人が同じ `createdAt` を持つので、`createdAt` だけをしおりにすると、ページの境目で同じ時刻の人が抜けたり重なったりする。`id` を足して `(createdAt, id)` で1行に決める
- **並ぶ向きが混ざると、条件を2つに分けて書く。** 今の並び順は `createdAt DESC, id`（`id` は昇順）なので、「しおりより後ろ」は `createdAt < ? OR (createdAt = ? AND id > ?)` になる。両方が同じ向きなら `(createdAt, id) < (?, ?)` と1つで書けるが、向きが混ざるとこの書き方では表せない
- **OFFSET は、ページをめくる間に行が増えたり減ったりするとずれる。** DB は前のページで何を見せたかを覚えておらず、ページごとに、その瞬間の並び順で数え直す。先頭に1人増えると全員の順位が1つ後ろにずれ、前のページの最後の人が次のページの先頭にもう一度出る（実験4）。逆に1人減ると、1人がどのページにも出なくなる。カーソル式は「この人より後ろ」で取るので、前に人が増えてもずれない（実験5）
- **使い分けは「絶対の位置」が要るかどうか。** OFFSET は「何番目」で指定するので、ページ番号・「N / M ページ」・「101〜150人目」・好きなページへ飛ぶ、ができる。カーソル式は「この人の次」なので、次へ・前へ・無限スクロールに向く。ページ番号や全体の件数は出せない。OFFSET で全体のページ数を出すには、リクエストのたびに `COUNT(*)` が要る（`listUsers` もそうしている）
- **カーソル式の API の形の定番。** 1件多く（51件）取って、51件目があれば「次がある」と分かる。しおりは Base64 などで包んだ文字列として返し、クライアントには中身を意識させない。クライアントは次のリクエストでそれをそのまま送る

### 数字で見た結果

`user_page`（50万行）に、1ページ50人で流した。時間は `EXPLAIN ANALYZE` の `actual time`。

| 実験 | SQL の形 | 読み方 | 読んだ行 | 時間 |
| -- | -- | -- | -- | -- |
| 1 | 索引なし、今の SQL（種別の `CASE` つき）の1ページ目 | `Table scan` → `Sort` | 50万行 | 450ms |
| 1 | 同じ SQL の1000ページ目（`OFFSET 49950`） | 同上 | 50万行 | 1,659ms |
| 1 | 同じ SQL の10000ページ目（`OFFSET 499950`） | 同上 | 50万行 | 1,882ms |
| 2 | `(createdAt DESC, id)` の索引を足して1ページ目 | `Index scan` | 50行 | 0.74ms |
| 2 | 同じ索引で10000ページ目 | 索引を使わず `Table scan` → `Sort` | 50万行 | 1,704ms |
| 3 | 10000ページ目と同じ50人を、カーソル式で取る | `Index range scan` | 50行 | 0.265ms（実験2の約6,400倍速い） |

### 面接で話す要点（STAR）

- **S（状況）**：管理画面の利用者一覧は `LIMIT ? OFFSET ?` で、ページ番号を出す。並び順は `createdAt DESC, id` で、`createdAt` の索引は無い
- **T（課題）**：OFFSET とカーソル式の違いを、速さと正しさの両方から、数字で説明できるようにしたかった
- **A（行動）**：本番と同じ形の利用者表を別のスキーマに50万行作り、今の SQL・索引を足した SQL・カーソル式を `EXPLAIN ANALYZE` で比べた。ページをめくる間に1人登録が入る場合も再現した
- **R（結果）**：最後のページは、OFFSET だと索引を足しても50万行を読んで 1,704ms、カーソル式は50行で 0.265ms（約6,400倍）だった。途中で1人増えると、OFFSET では前のページの最後の人が次のページに重複し、カーソル式では重複しなかった。管理画面はページ番号が要り、見るのも管理者だけなので OFFSET が合う。カーソル式が向くのは、学習記録のように件数が増え続け、次へ読み進める一覧だと説明できるようになった

## 2-2 冪等性（学習記録の作成の二重送信）（2026-10-21）

題材は学習記録の作成（`POST /api/study-logs`）。開発用の DB（`juken_map`）に、ローカルの撮影用の利用者でログインして curl で流した。並行の確かめは、テスト用の DB（`juken_map_test`）に Go のテストで流した。

### 学んだこと

- **POST は冪等ではない。困るのは「保存は成功したのに、応答だけ失われた」とき。** 画面には失敗に見えるので、利用者は押し直す。サーバーは2回目を新しい操作として受け取り、2件目を作る。サーバーが断ったと分かっている失敗（400 など）なら、押し直しても困らない
- **冪等キーは「この操作は何回目か」を伝える札。** 画面が操作ごとにキーを作り、送り直しでは同じキーを送る。サーバーは、そのキーで保存済みなら新しく作らず、1回目の結果を返す。2回目の応答には `Idempotent-Replayed: true` を付けて、送り直しだと分かるようにした
- **キーを新しくするのは「保存された」と分かったときだけ。** 成功（201）なら保存された。422（同じキーで保存済み）でも保存されている。4xx はサーバーが DB に書く前に断ったもので、5xx と通信の失敗（`TypeError`）は、保存されたか分からない。どちらもキーを変えずに送り直す。保存されていなければ、そのキーで1回目として記録される
- **同じキーで本文が違えば 422。** 本文の SHA-256 を一緒に残して比べる。1回目が保存されたのに気づかず、内容を直して送り直したときに起きる。黙って1回目の結果を返すと、直した内容が捨てられたことに気づけない。画面は一覧を読み直し、「既に保存されています」と出す
- **2回目の応答も、1回目とそろえる。** 「初めての記録か」（`isFirstStudyLog`）は記録の行に残らないので、キーの行に残した。残さないと、送り直したときに「初回」が false になり、初回の計測が抜ける（実験1で、キーなしの2回目は false になった）
- **キーの行は、記録と同じトランザクションの最初に INSERT する。** 同じキーで同時に届いた2本目は、主キーのロックで1本目のコミットを待ち、コミットされたら重複（1062）になってから1回目の結果を読む。先に SELECT で「あるか」を見てから作ると、同時の2本がどちらも「無い」と見て2件になる。1本目が失敗して取り消されると、キーの行も消えるので、2本目がそのまま記録できる
- **外部キーの確かめは、親の行に共有ロックを取る。** キーの行の `userId` に外部キーを付けたら、同じ利用者が別々のキーで同時に記録したとき、10本中9本がデッドロック（1213）になった。それぞれの INSERT が `user` の行に共有ロックを取り、続く初回記録の印（`UPDATE user`）の排他ロックをお互いに待ったため。`userId` の外部キーを外して直した。利用者を消すと実績が消え、実績が消えるとキーの行も消えるので、行は残らない（テストで確かめた）
- **キーの列は `ascii_bin` にする。** 表の既定の `utf8mb4_unicode_ci` は大文字と小文字を同じとみなすので、別のキーが同じキーとして扱われる
- **守れない場合もある。** 画面を閉じたり読み直したりするとキーは作り直される。その後の送り直しは2件になる。キーをいつまで残すか（期限と後片付け）は、まだ決めていない

### 数字で見た結果

| 実験 | 流したもの | 結果 |
| -- | -- | -- |
| 1 | キーなしで、同じ本文を2回 POST | 2件できた。`isFirstStudyLog` は1回目 true・2回目 false |
| 2 | 同じキーで、同じ本文を2回 POST | 2回とも 201 で、同じ id。2回目に `Idempotent-Replayed: true` |
| 3 | 同じキーで、本文を変えて POST | 422。件数は増えない |
| 4 | 形の違うキー（英数字とハイフン以外を含む） | 400 |
| 5 | キーなしで10本同時 | 10件 |
| 6 | 同じキーで10本同時 | 1件。10本とも 201 で、同じ id |
| 7 | 同じ利用者が別々のキーで10本同時（`userId` に外部キーあり） | 9本がデッドロック（1213） |
| 8 | 7 と同じ（外部キーを外したあと） | 10件。並行のテストを20回流して、すべて通った |

### このリポジトリの今

本番には入れない（2026-10-21 判断）。学習記録の作成（`study_log_writes.go` の `Create`）に冪等キーは無く、送り直すと2件になるのは今までどおり。

入れるなら、キーの行をいつまで残すか（期限）と、古い行を消す仕組みを先に決める。キーの行は記録1件につき1行増え、今は消えるのが記録を消したときだけなので、放っておくと記録と同じだけ増え続ける。画面のタイマーで記録する経路（`useStudyLogs.ts` の `saveStudySession`）にも、同じようにキーを持たせる。

### 面接で話す要点（STAR）

- **S（状況）**：学習記録の作成は POST で、保存は成功したのに応答だけ失われると、押し直したときに2件になる
- **T（課題）**：送り直しを1件にしたい。ただし本当に別の記録は断らず、同時に送られても崩れないようにする
- **A（行動）**：画面が操作ごとに冪等キーを作り、保存されたと分かるまでは同じキーで送り直すようにした。サーバーはキーの行を記録と同じトランザクションの最初に入れ、主キーの重複で2回目を見分けて、1回目の結果を返す。同じキーで本文が違えば 422 にした
- **R（結果）**：同じキーで10本同時に送っても1件になり、10本とも同じ記録を返した（キーなしでは10件）。途中で、外部キーの共有ロックによるデッドロック（10本中9本）を見つけ、外部キーを外して直した。外しても行が残らないことはテストで確かめた
