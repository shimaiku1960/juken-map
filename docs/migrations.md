# マイグレーションの書き方

テーブル定義を変える SQL（`db/migrations/<YYYYMMDDHHMMSS>_<内容>/migration.sql`）を書くとき・レビューするときの決まり（JUK-144）。
当てる仕組み（`migrate` コマンド・記録の表・DB ユーザーの分け方）は [architecture.md](./architecture.md) の「マイグレーション（テーブル定義の変更）」にある。
ここに書いた決まりの根拠は、手元で再現した実験（[learning/db.md](./learning/db.md) の「1-5 マイグレーションの安全な運用」）。

## なぜ決まりが要るか

本番のデプロイ（`.github/scripts/deploy-ec2.sh`）は、次の順で動く。

1. マイグレーションを当てる（このとき動いているのは**古いアプリ**）
2. 新しいコンテナを起こし、ヘルスチェックを待つ
3. nginx を新しいコンテナへ向ける
4. 5秒待って、古いコンテナを止める

ここから、マイグレーションには次の4つの条件が付く。

- **古いアプリが新しい表で動くこと。** 1〜4 の間、古いアプリは新しい表の形で読み書きする。2 で新しいコンテナが落ちたら古いアプリが残り、
  スモークテストが落ちたら前のイメージに戻るが、どちらの場合も表は新しいまま。
- **新しいアプリが、ひとつ前の表で動く必要は無いこと。** マイグレーションは必ずアプリより先に当たる。
- **戻せないこと。** MySQL の CREATE / ALTER / DROP はトランザクションで取り消せず、down（逆向きのマイグレーション）も書いていない。
  間違えたら、新しいマイグレーションを足して前に進めて直す。
- **ALTER の間も、表には本番のリクエストが来ていること。** ALTER が表を長く押さえると、その表を使う画面が全員分止まる。

1つ目と2つ目は表の**形**の問題で、変更を何回のデプロイに分けるかで解く。4つ目は**時間**の問題で、ALTER の書き方で解く。

## 決まり1：古いアプリが動く形に分ける（足す → 移す → 消す）

| やりたい変更 | 分け方 |
| -- | -- |
| 表を足す | 1回でよい |
| 列を足す | 1回でよい。ただし **NULL 可にするか、`DEFAULT` を付ける**。古いアプリはその列を知らないので、INSERT で書かない。既定値の無い `NOT NULL` の列を足すと、古いアプリの INSERT が `Field doesn't have a default value` で落ちる |
| 既定値の無い `NOT NULL` の列を足す | 3回：①NULL 可で足し、アプリが書くようにする ②空の行を埋める ③`NOT NULL` に締める |
| 列の名前を変える・型を変える | 3回（下の表）。`RENAME COLUMN` を1回で流すと、古いアプリが `ERROR 1054 Unknown column` になる（実験1） |
| 列・表を消す | 2回：①アプリが読み書きしないようにする（`NOT NULL` で既定値が無い列なら、ここで NULL 可にする）②次のデプロイで消す |
| 索引を足す・消す | 1回でよい。ただし大きな表では時間がかかる（決まり2） |

列の名前を変える3回は、次のとおり。

| デプロイ | マイグレーション（古いアプリが動いている間に当たる） | アプリ |
| -- | -- | -- |
| 1 足す | 新しい列を NULL 可で足す | 両方の列に書き、古い列を読む |
| 2 移す | 空の行を古い列から埋める（バックフィル） | 新しい列だけを読み書きする |
| 3 消す | 新しい列を `NOT NULL` に締め、古い列を消す（ALTER が2本なのでファイルも2つ） | 変えない |

- **バックフィルは、両方に書くアプリを出した次のデプロイに入れる。** `UPDATE` は流したその時点の行しか直さない。
  両方に書くアプリと同じデプロイに入れると、マイグレーションが切り替えより先に流れるので、そのあと古いアプリが作った行が空のまま残り、
  3 の `NOT NULL` が失敗する。
- **バックフィルは何度流しても壊れない形にする。** `UPDATE t SET new = old WHERE new IS NULL` のように、埋まっていない行だけを直す。
- **古い列が `NOT NULL` で既定値が無いなら、1 で NULL 可にしておく。** 2 のアプリが古い列を書かなくなるため。
- **2 を前のイメージに戻すと、2 の間に作られた行は古い列が空になる。** 戻しても困らないようにしたいなら、2 のアプリも両方に書き、
  古い列を書くのをやめるデプロイを1回足す（4回になる）。
- **消す前に、本番で使われていないことを確かめる。** 閲覧用ユーザー（`juken_readonly`）で行数や最終更新を数え、確かめた内容を
  migration.sql の冒頭に書く（例：`20261005090000_drop_unused_personal_data`）。

## 決まり2：ALTER がどれだけ表を押さえるかを、流す前に決める

ALTER には、**定義だけを変える**もの（行数によらず一瞬）と、**全部の行を書き直す**もの（行数に比例して時間がかかる）がある。
`ALGORITHM=` を書かないと MySQL が黙ってやり方を選ぶので、思ったより重い変更でも気づけない。

- **既にある表への ALTER には、必ず `ALGORITHM=` を書く。** 書いたやり方でできない変更は、流す前に `ERROR 1845` / `ERROR 1846` で止まる。
  - `ALGORITHM=INSTANT`：定義だけを変える。`LOCK=NONE` などは付けない（付けると `ERROR 1221`）
  - `ALGORITHM=INPLACE, LOCK=NONE`：書き直しの間も読み書きを止めない。最中の変更は MySQL が控えておき、最後に反映する
  - どちらも通らない（`Try ALGORITHM=COPY`）なら、書き直しの間は**書き込みが止まる**。行数が少ない表に限り `ALGORITHM=COPY` と書いて流し、
    行数を冒頭のコメントに書く。大きな表は gh-ost / pt-online-schema-change のような道具が要る（まだ用意していない）
- **1本の ALTER に混ぜてよいのは、同じ `ALGORITHM` で済む変更だけ。** 速い変更と遅い変更を1本にすると、全体が遅い方に合わせて書き直しになる（実験3）。
- **1つのファイルに、既にある表への ALTER は1本にする。** `migrate` はファイルを1回で流すので、2本目で失敗すると1本目だけが当たった状態で止まる。
  1本なら「当たった・当たっていない」のどちらかだけになり、直し方が決まる（決まり4）。新しく作る表だけのファイルは、CREATE TABLE が複数でもよい。

MySQL 8.4 で確かめた主な変更（2026-10-20、手元の使い捨てスキーマで流した）：

| 変更 | 書く指定 |
| -- | -- |
| 列を足す（NULL 可・`DEFAULT` 付き） | `ALGORITHM=INSTANT` |
| 列の名前を変える・列を消す・既定値を変える | `ALGORITHM=INSTANT` |
| 索引を足す・消す・見えなくする（`ALTER INDEX ... INVISIBLE`） | `ALGORITHM=INPLACE, LOCK=NONE` |
| NULL 可 ⇔ `NOT NULL` | `ALGORITHM=INPLACE, LOCK=NONE`（書き直しになる） |
| `VARCHAR` を伸ばす | 長さを表すバイト数が変わらない範囲だけ `INPLACE`。utf8mb4 の `VARCHAR(50)→(60)` は通り、`(50)→(100)` は COPY になる |
| 型を変える（`INT→BIGINT` など） | COPY。決まり1の3回に分ける |
| 既にある表に外部キーを足す | COPY（`foreign_key_checks` を切らない限り） |

時間の目安：1,069万行の表（手元）に索引を足したとき、16.9秒かかり、その間も読み書きは止まらなかった（dev-standards `projects/juken-map/`）。

## 決まり3：ロックを待つ時間に上限を付ける

`INSTANT` でも、始めと終わりには表を独り占めする（メタデータロック）。その表を使っているトランザクションが1つでもあれば、ALTER はその終わりを待つ。
待っている ALTER の後ろには、ふつうの SELECT まで並んで止まる（実験4）。待つ時間の既定は1年（`lock_wait_timeout = 31536000`）。

- **既にある表への ALTER の前に、`SET SESSION lock_wait_timeout = 5;` を書く。** 上限を超えると ALTER は `ERROR 1205` で諦め、後ろの SELECT は流れ出す。
  マイグレーションは新しいコンテナより先に流れるので、失敗してもデプロイがそこで止まり、古いアプリが動き続ける。
  全員を待たせるより、マイグレーションが失敗して流し直すほうがよい。
- 失敗したら、決まり4の手順で記録を直してから、もう一度デプロイする。

`migrate.go` は `GET_LOCK` で二重に当てるのを防いでいるが、`lock_wait_timeout` は設定していない。そのため今はファイルごとに書く。

## 決まり4：当てたあとは書き換えず、前に進めて直す

- **当てた migration.sql は書き換えない。** 書き換えても DB には反映されず、`migrate` が警告を出すだけ。直すときは新しいマイグレーションを足す。
- **途中で失敗すると、記録の表 `_prisma_migrations` に「終わっていない」行が残り、人が直すまで次のデプロイの `migrate` も止まる。**
  ALTER を1本にしておけば、失敗したファイルは何も当たっていない。その行の `rolled_back_at` を埋めると、次のデプロイで同じファイルがもう一度流れる。
  手で当て終えたなら `finished_at` を埋める。
- **データの移行（`UPDATE`）とテーブル定義の変更（ALTER）は別のファイルにする。** 同じファイルにあると、片方だけ当たった状態で止まることがある。
  ALTER は暗黙にコミットするので、まとめて取り消すこともできない。
- **大きな表のバックフィルは migration.sql に書かない。** 1本の `UPDATE` で全部の行を直すと、その間、直している行をほかの書き込みが待つ。
  目安として10万行を超えるなら、id の範囲で区切って少しずつ流す。そのための道具はまだ無いので、要るときに作る。

## 決まり5：索引は EXPLAIN で確かめる

- **足す前と後に、その索引を使うはずの SQL を `EXPLAIN` する。** 足す前は `type: ALL`（全行を読む）や `rows` が大きいこと、
  足した後は `key` にその索引が出て `rows` が減ることを確かめ、数字を migration.sql の冒頭に書く（例：`20260915090000_add_user_date_indexes`）。
- **消す前に、いきなり消さずに見えなくする。** `ALTER INDEX ... INVISIBLE` にすると、索引は保たれたまま、照会に使われなくなる。
  遅くなる照会が無いことを確かめてから、次のデプロイで消す。遅くなったら `VISIBLE` に戻せば、作り直さずに済む。
- **外部キーの列の索引を置き換えるときは、足すのと消すのを同じ ALTER に入れる。** 外部キーには、その列を左端に持つ索引が要る。
  1本にすれば、索引の無い瞬間ができない（どちらも `INPLACE` なので混ぜてよい）。

## レビューの確かめ方

マイグレーションを含む PR は、CI が通ってもマージせずユーザーに確認する（AGENTS.md）。その前に、次を確かめる。

- [ ] 古いアプリ（今の main）が、この表の形で読み書きできる（列の削除・名前の変更・既定値の無い `NOT NULL` が無い。あれば決まり1で分けてある）
- [ ] バックフィルは、両方に書くアプリを出したデプロイより後にある
- [ ] 既にある表への ALTER は、ファイルに1本で、`ALGORITHM=` が書いてある
- [ ] `ALGORITHM=COPY` や大きな表への `INPLACE` は、行数と時間の見込みが冒頭のコメントにある
- [ ] ALTER の前に `SET SESSION lock_wait_timeout = 5;` がある
- [ ] `UPDATE` と ALTER が同じファイルに無い
- [ ] 当て済みの migration.sql を書き換えていない
- [ ] 索引を足す・消すなら、`EXPLAIN` の前後の数字がある
- [ ] その列を読み書きする Go の SQL と struct、応答に出る列なら `openapi/openapi.yaml` も合わせてある

CI が確かめるのは、空の DB に全部のマイグレーションを当てられること（`TestMigrateDB`、E2E の前の `pnpm run db:migrate`）まで。
古いアプリと新しい表の組み合わせと、`ALGORITHM=` の書き忘れは、まだ CI で確かめていない。

## 例

**分けるべきだった例**：`20260710112248_add_textbook_and_study_range` は、列の追加4つ（定義だけの変更）と `MODIFY content TEXT NULL`（書き直し）を1本の ALTER にしている。
そのため `StudyPlan` を丸ごと書き直していたはず（当時は行が少なく問題にならなかった）。今の決まりで書くなら、2つのファイルに分ける。

```sql
-- 1つ目のファイル：定義だけの変更
SET SESSION lock_wait_timeout = 5;
ALTER TABLE `StudyPlan`
    ADD COLUMN `rangeEnd` INTEGER NULL,
    ADD COLUMN `rangeStart` INTEGER NULL,
    ADD COLUMN `rangeUnit` VARCHAR(191) NULL,
    ADD COLUMN `textbookId` INTEGER NULL,
    ALGORITHM=INSTANT;
```

```sql
-- 2つ目のファイル：書き直しになる変更。StudyPlan は○万行で、手元で○秒（流す前に測って書く）
SET SESSION lock_wait_timeout = 5;
ALTER TABLE `StudyPlan` MODIFY `content` TEXT NULL, ALGORITHM=INPLACE, LOCK=NONE;
```

**よい例**：

- `20261005090000_drop_unused_personal_data`：アプリが読み書きしなくなったあとで、本番を閲覧用ユーザーで数えて使われていないことを確かめてから消している。
  確かめた内容が冒頭に書いてある。
- `20260915090000_add_user_date_indexes`：索引を足す理由と検証の数字（36.9万行で 268ms → 1.75ms）が冒頭にあり、
  外部キーが索引を失う瞬間を作らないよう、足すのと消すのを1本の ALTER に入れている。今の決まりで書くなら、`ALGORITHM=INPLACE, LOCK=NONE` を足し、表ごとにファイルを分ける。
